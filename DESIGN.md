# DESIGN — Homework 1 changes

This document explains the architecture and design of the service-based components added for Homework 1. It documents how the FastAPI service, the auto-generated HTTP client, and the adapter (shim) work together so that existing code written against the original library continues to work unchanged.

## Architecture overview

- Goal: turn the library-based Gmail implementation into a network service so multiple programs can share a single, long-running connection to the mail provider.
- Three new bridges added:
  - FastAPI service (backend) — `src/mail_client_service/src/main.py`
  - Auto-generated HTTP client — `src/generated_client/mail_client_service_client` (OpenAPI client). Note: the repository includes the generated package under this nested path; the adapter expects a top-level `generated_client` import so a small shim (`src/generated_client/__init__.py`) or editable install may be required for local runs.
  - Adapter / Service shim — `src/adapter/service_client_adapter.py` which implements the original `mail_client_api.Client` interface but forwards requests to the generated HTTP client.

Key property: user code does not change. The adapter implements the same interface as the original library so callers swap in the adapter instead of the concrete Gmail library and call the same methods.

## Components

- mail_client_api (existing): the abstract contract (ABC) the project exposes. Consumers call `mail_client_api.get_client()` or type-hint against `mail_client_api.Client`.
- gmail_client_impl (existing): original concrete Gmail implementation that knows how to talk to Gmail's API and handle OAuth. Left unchanged — the service uses it under the hood.
- mail_client_service (new): a thin FastAPI wrapper around the `mail_client_api` factory. Important files:
  - `src/mail_client_service/src/main.py` — defines endpoints:
    - `GET /messages` — returns a list of message summaries
    - `GET /messages/{message_id}` — returns full message detail
    - `POST /messages/{message_id}/mark-as-read` — marks message as read
    - `DELETE /messages/{message_id}` — deletes message
  - The service resolves a `Client` instance via `get_client_dep()` which calls `mail_client_api.get_client(interactive=True)`; this means the service delegates all logic and auth to the existing implementation.
- generated_client (new): an auto-generated OpenAPI client (under `src/generated_client/mail_client_service_client`) that provides a programmatic client for the FastAPI service endpoints. The adapter uses this client.
- adapter.ServiceClientAdapter (new): implements `mail_client_api.Client` and translates calls into generated-client HTTP calls. It also wraps generated-client models into objects that implement the `Message` contract (see `ServiceMessage`).

## Request flow (one request, end-to-end)

Example: consumer code calls `client.get_message('m123')` where `client` is a `ServiceClientAdapter` instance.

1. Consumer calls `ServiceClientAdapter.get_message('m123')`.
2. The adapter uses the generated client: `AutoGeneratedClient.messages.get_message.sync(message_id='m123')` and receives a JSON response parsed into `MessageDetail` model.
3. Adapter wraps the returned model in `ServiceMessage` (implements the `Message` contract) and returns it to the caller.
4. Behind the generated client, an HTTP request is sent to the FastAPI service endpoint `GET /messages/{message_id}`.
5. FastAPI's `get_message_detail` endpoint uses the dependency `get_client_dep()` to obtain a concrete `gmail_client_impl.GmailClient` instance (via the `mail_client_api` factory).
6. The service calls `gmail_client_impl.GmailClient.get_message(message_id)` (local, in-process) and returns the result as JSON.
7. Generated client receives JSON and the adapter returns the wrapped `ServiceMessage` to the original caller.

Diagram (linear):

user code → adapter (ServiceClientAdapter) → generated client (HTTP) → FastAPI service (/messages/...) → gmail_client_impl (local) → FastAPI → generated client → adapter → user code

## Sample API responses

- GET /messages (200):

```json
[
  {"id": "m1", "subject": "Subject 1"},
  {"id": "m2", "subject": "Subject 2"}
]
```

- GET /messages/m1 (200):

```json
{
  "id": "m1",
  "from_": "alice@example.com",
  "to": "me@example.com",
  "date": "2025-01-01T00:00:00Z",
  "subject": "Subject 1",
  "body": "Hello from dummy"
}
```

- POST /messages/m1/mark-as-read (200):

```json
{ "ok": true, "message": "Message 'm1' marked as read" }
```

- DELETE /messages/m1 (200):

```json
{ "ok": true, "message": "Message 'm1' deleted successfully" }
```

## API Design

Endpoints (summary):

- GET /messages
  - Query params: `limit` (int, default 10)
  - Response: JSON array of `{ id, subject? }`

- GET /messages/{message_id}
  - Response: MessageDetail JSON: `{ id, from_, to, date, subject, body }`

- POST /messages/{message_id}/mark-as-read
  - Response: `{ ok: bool, message?: str }`

- DELETE /messages/{message_id}
  - Response: `{ ok: bool, message?: str }`

Error handling

- Service maps internal exceptions to HTTP errors using FastAPI's `HTTPException`:
  - If `get_client_dep()` fails to initialize the client: 500 Internal Server Error (service-side init failure).
  - If `client.get_message()` raises an exception while fetching a specific message: 404 Not Found (message not found or cannot be retrieved).
  - If an action returns `False` (like delete or mark-as-read): 400 Bad Request with an explanatory detail.
  - Unexpected exceptions while iterating / processing messages: 500 Internal Server Error.

Rationale: keep the mapping simple and predictable so clients can handle 4xx for client-caused problems and 5xx for server-side failures.

## The Adapter pattern

Why it's needed

- The auto-generated client provides convenience wrappers for HTTP endpoints, but its API surface and model classes do not match the original `mail_client_api.Client` interface exactly. The adapter provides a stable interface that callers expect and translates that into generated-client calls.

How it works (example)

User code calling the original library (unchanged):

```py
from mail_client_api import get_client

client = get_client(interactive=False)  # previously returned GmailClient
for m in client.get_messages(max_results=5):
    print(m.id, m.subject)

msg = client.get_message('m1')
print(msg.body)
```

User code calling the adapter (identical):

```py
from adapter.service_client_adapter import ServiceClientAdapter

adapter = ServiceClientAdapter(base_url="http://localhost:8000")
for m in adapter.get_messages(max_results=5):
    print(m.id, m.subject)

msg = adapter.get_message('m1')
print(msg.body)
```

Adapter implementation details (short):

- `ServiceClientAdapter` constructs the generated client: `AutoGeneratedClient(base_url=...)`.
- It calls generated-client methods and maps returned `MessageDetail` / `MessageSummary` into `ServiceMessage` which implements the `Message` contract from `message` / `mail_client_api`.

## Testing strategy

What we tested

- Integration test that verifies adapter → service → client wiring using a test double (`DummyGmailClient`) injected into the FastAPI app. File: `tests/integration/test_client_integration.py` (`test_adapter_service_integration`).
- E2E tests that execute the `main.py` script in both local-credentials and CI env-var modes (see `tests/e2e/test_main_application.py`).

Test types and rationale

- Unit tests: (not added here) should test small functions in isolation — e.g., model parsing helpers.
- Integration tests: we added `test_adapter_service_integration` to ensure the adapter implements the interface and that HTTP → service → implementation flow works. This test uses `fastapi.TestClient` so no network is required.
- E2E tests: `tests/e2e/test_main_application.py` runs `main.py` as a subprocess and verifies full, real authentication flows when credentials are available.

Mocking strategy

- For adapter→service integration we inject a `DummyGmailClient` using FastAPI's `dependency_overrides` (`mail_app.dependency_overrides[get_client_dep] = lambda: dummy`). This isolates network layers and provides deterministic responses.
- For E2E tests we run the actual `gmail_client_impl` (real credentials required) — these tests are gated using pytest markers (`local_credentials`) so CI does not run them unless credentials are provided via the protected CircleCI context.

Interface compliance

- The adapter class `ServiceClientAdapter` subclasses the abstract `Client` and returns objects compatible with the `Message` contract via `ServiceMessage`.
- Compliance is validated by the integration test which:
  - Instantiates `ServiceClientAdapter(base_url=TestClient.app.base_url)`,
  - Calls `get_messages()` / `get_message()` / `mark_as_read()` / `delete_message()` and asserts the expected behavior and object shape.

## How to run the verification locally

- Adapter integration test (fast, in-process):
```bash
PYTHONPATH=src pytest -o addopts= tests/integration/test_client_integration.py::test_adapter_service_integration -q -rs
```

- E2E tests requiring credentials (local only):
```bash
export GMAIL_CLIENT_ID=... \
       GMAIL_CLIENT_SECRET=... \
       GMAIL_REFRESH_TOKEN=...
PYTHONPATH=src pytest -m "integration and not local_credentials" -v
```

## Open issues and next steps

- Import path mismatch: the adapter imports `from generated_client import Client as AutoGeneratedClient` while the generated package lives under `src/generated_client/mail_client_service_client`. Two acceptable fixes:
  1. Add a tiny shim `src/generated_client/__init__.py` that re-exports the generated client (quick), or
  2. Install the generated package in editable mode: `python -m pip install -e src/generated_client`.
- Consider adding typed adapter tests and a minimal unit-test suite for `ServiceMessage` mapping.
